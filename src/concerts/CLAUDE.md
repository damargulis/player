# src/concerts/ — the concert tracker

## Concert tracker

`src/concerts/` tracks upcoming shows near the listener by artists in the library. Data comes from the **JamBase Data API** (`api.data.jambase.com/v3`, `Authorization: Bearer` with `JAMBASE_API_KEY` from the usual env files) — Songkick is partner-only now and Bandsintown's keys are scoped to a single artist, so neither can serve a whole library. The design is one cheap **location sweep** (`/events?geoLatitude&geoLongitude&geoRadiusAmount&geoRadiusUnits&eventDateFrom&eventDateTo&perPage=100&expandExternalIdentifiers=true`) rather than a lookup per artist: Performers are matched to library artists **by name** (`performerMatches` in `store.tsx`): the exact folded name via `nameKey`, never a partial one, and for a name of four characters or fewer a genre in common as well, since a JamBase "Bob" or "44" at a bar is rarely the artist in the library. It used to match exactly on MusicBrainz id via `expandExternalIdentifiers`, but JamBase moved that parameter to its paid Startup plan in November 2026 and every sweep then failed — and dropping the parameter alone would have matched nothing, since the ids were the only key. `GENRE_ALIASES` widens JamBase's slugs (`edm`, `hip-hop-rap`) to the words a library genre uses. The free Developer tier allows **1000 calls/month**, so `store.tsx` tracks usage, refuses to sweep when spent, and only refreshes when the cache is older than **24h** — a dense metro is ~24 pages a sweep, so twice-daily would cost ~1500/month. Radius barely affects cost (15mi is 23 pages, 40mi is 26), so prefer a generous radius over a tight one. **Use my location** tries the OS first and falls back to IP. `navigator.geolocation` in Electron on macOS does reach CoreLocation (an unprivileged attempt fails with *"User has not allowed access to system location"*, which is macOS talking, not Chromium) — but only from a secure origin and only once the bundle declares `NSLocationWhenInUseUsageDescription` (set via electron-builder `mac.extendInfo`) **and** Location Services has been granted to MyMusic in System Settings. `session.setPermissionRequestHandler` must also allow it, or Electron denies the request before macOS sees it. The IP fallback uses `ipapi.co` (JamBase's own `geoIp` reports its servers, not the caller) and is ISP-accurate to a few miles, hence the "(approx.)" label. Results live in `DATA_DIR/concerts.json` — deliberately *not* in `library.json`, which is large, backed up daily, and must not churn with volatile data. A 🎟️ appears beside the now-playing artist whenever they have a show coming up — in `InfoPanel.tsx`, which both the full header and the mini player render, so one badge covers both; it reads the cache via `concertsForArtists` (a memoised artist→shows index dropped inside `saveCache`, the only writer) and never fetches, so it costs no API calls. `ConcertsPage.tsx` is the tab — a date-ordered list (sortable by play count) or a month calendar whose dots are sized by plays and coloured for favourites, filterable, with a city picker backed by `/geographies/cities?geoCityName=`. **`isUpcoming` in `concerts/store.tsx` is the only definition of "not in the past" — every view must go through it** (the tab, `ArtistConcerts`, the badge, and the DJ's `concertInfo`). The cache keeps a show until the next sweep and sweeps are daily at best, so anything filtering the raw cache will eventually present a finished gig as upcoming; three separate copies of the logic existed and only one checked the date. Parse show dates with `localDate` from `src/utils.tsx`, never `new Date(iso)`: a date-only value like `2027-01-14` is read as UTC midnight and renders as the 13th anywhere west of Greenwich; `ArtistConcerts.tsx` shows the same cached data on an artist page and renders nothing when there's nothing. Newly announced shows are diffed on each refresh (`findUnseen`) and carried forward across refreshes until the tab is opened, so nothing is lost between visits; the "N newly announced" badge is a **toggle** that filters the list and calendar to just those, and keeps working after the sidebar badge clears because `highlighted` outlives `markSeen`. `matchesFilter` lives in `concerts/store.tsx` beside `isUpcoming` so the list and calendar cannot disagree about what is shown; the count reaches the sidebar through `concerts/alerts.tsx`, a tiny subscribable store rather than Redux, since it derives from a file on disk and only two components care. JamBase requires visible attribution, which is in the tab footer.

## Dates and cost

- Every "what day is it" here goes through `localDayKey` (`src/utils.tsx`), never
  `toISOString().slice(0, 10)`. The calendar's `todayKey` and the sweep's `eventDateFrom` both used
  the UTC day, so each evening the calendar highlighted tomorrow and a refresh dropped tonight's
  shows.
- `ConcertsPage`'s `mapStateToProps` totals plays per artist over every track; it is memoised on
  the library (`rollupOf`). Unmemoised it cost 5.25ms per redux action, about four a second through
  playback, for the same answer. The 90-day "recent" window reads the clock, so a cached result can
  go a little stale; a day's resolution makes that harmless.
